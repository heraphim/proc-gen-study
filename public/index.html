Procedural Generation Catalogue

Procedural generation

Content described by a process rather than stored as data. You ship the rule that makes the thing, not the thing.

What it actually buys you

Five reasons, and they are not interchangeable — most projects want exactly one, and picking the wrong one is how generators end up costing more than the assets they replaced.

Volume

More content than anyone could author. 18 quintillion planets. A million guns. This is the reason people quote, and the one that most often disappoints — see the oatmeal problem in Pitfalls.

Variation

The same thing, never identical twice. Footstep sounds that don't repeat, crowds where no two faces match, wear patterns unique to each object.

Adaptation

Content that responds at runtime to something you couldn't know in advance — the player's skill, the shape of the data, the time of day, the size of the screen.

Compression

A seed is smaller than a world. Elite's universe was six bytes. A 96 KB executable holds a whole first-person shooter. Bandwidth and memory, not disk.

Search

Exploring a design space no human would walk through by hand — evolved antennas, topology-optimised brackets, protein backbones, drug candidates. Here the generator isn't saving labour, it's finding things people wouldn't.

Where it's used

The word changes by industry, which is why the field looks smaller than it is. Games call it procedural generation. Engineering calls it generative design. Operations research calls it optimisation. Statistics calls it simulation. Biology calls it in silico design. They are substantially the same activity: declare constraints and a process, let a machine emit an artefact.

A short history

Dates and citations below are verified. The through-line is that almost every technique arrived from outside entertainment — biology, mathematics, architecture — and was borrowed later.

    How this project structures it

    The catalogue arrived as a flat list of 841 things, tagged with 28 labels. That structure mixed several different kinds of object, which made it impossible to say what any entry actually was. What follows is the model being rebuilt in its place.

    Concepts

    Ideas about what can be made, at every grain. Noise is a coarse concept; cobblestone paving is a fine one. They differ in grain, not in kind, so they live in one table connected by uses edges.

    — building blocks

    A concept that is irreducible, used across unrelated domains, and has something concrete you could import. Randomness, Voronoi, noise, cellular automata. Roughly fifteen of them. Everything else is built out of these.

    Test: simulation is used in 21 of 23 domains, more than anything except randomness — and it fails, because there is no "simulator" you can import. It's a category, not a block. That is exactly why it became a dumping ground.

    Algorithms

    Named, published, pinned-down methods. Perlin noise. Fortune's sweepline. FABRIK. Knuth–Plass. This is the only level that has papers, which is why the catalogue has no citations today — it never had this layer. Some concepts have an algorithm; many, like cobblestone paving, have none of their own and only wire others together.

    Implementations

    Runnable code implementing an algorithm. Packages, libraries, solvers. Separate from authoring applications like Houdini, which a human opens rather than a program calls.

    Technologies

    Languages and runtimes. A separate axis entirely — JavaScript, Python, Node, the GPU. Not a property of a concept, a property of where its code can execute.

            The three layers

            Every entry is classified as a source, an operator or a generator. The split exists because the reusable machinery and the named things people ask for are not the same kind of object, and the catalogue originally filed them side by side as though they were.

            1

            Does anything go in?

            If no — it's a source. You hand it a seed and some settings; it hands you structure. perlin(x, y, seed) needs nothing that exists in the world. Neither does a PRNG or Poisson disk sampling.

            2

            Something goes in — can you say what comes out without knowing what it's for?

            If yes — it's an operator. Hydraulic erosion takes a heightfield, returns a heightfield with valleys cut into it. You can describe it completely without using the word "terrain" — which is why the same code also weathers a texture and ages a metal surface. It doesn't know what the heightfield means.

            3

            Can you only explain it by naming the result?

            Then it's a generator. "A fantasy world map." "A staff roster." "A castle." There is no description that isn't just saying what it is.

            A generator isn't a different kind of code — it's a wiring diagram over the other two. That's why the generator layer is thin and the operator layer is fat.

            The same maths lands in different layers

            This is the part that trips people up. The layer is not a property of the algorithm — it's a property of how the entry is written. All three of these are Voronoi:

            "Voronoi diagrams" names an operation. "Cobblestone paving" names a thing you'd point at. Same code, different layer, because the entry is doing a different job.

            Why separate them

            Operators get reused across domains; generators don't. Written once, hydraulic erosion serves terrain, textures, weathering and ruins. Without the separation you write it several times without noticing — which is roughly what the catalogue's structure encourages, since erosion currently appears scattered across three domains as though it were three different things.

              Judgement calls worth arguing with

                Algorithms

                Named, published methods. The only level of the model that has papers — which is why the catalogue had no citations before this table existed.

                Candidates

                Names pulled out of the catalogue's description prose and out of the category concepts. Each needs its citation checked before it gets a row — so none of them are in the database, and no query over algorithm will ever return something unsourced. This is the queue, not a claim.

                Implementations

                Runnable code, grouped by concept and then by the specific algorithm it implements, with the technologies it runs on. Every row was resolved against its registry before being written down.

                A package appears under every algorithm it implements, so the card count is larger than the package count. That is deliberate: scipy under Delaunay, Halton, Sobol, Poisson disk, B-splines and simplex is six answers to six different questions, and one row under “Voronoi” answered none of them.

                Technologies

                A separate axis. Not a property of an idea — a property of where its code can run.

                Sources

                Every URL consulted while checking something, with the question it answered and what it bears on. Not a reading list — a reading list says what is worth reading, this says what was actually used, for which claim.

                Relations

                A source is attached to a concept, an algorithm, an implementation or a technology, with the kind of work it did. corrects is the one that matters most: it marks a source that overturned something this catalogue had already asserted.

                Corrections

                What this catalogue said, what it says now, and why. Kept as rows rather than quiet edits, because a catalogue that silently corrects itself gives you no way to judge how often it is wrong.
